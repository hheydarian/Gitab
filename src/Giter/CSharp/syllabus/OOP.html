🏗️ Object-Oriented Programming (OOP)

مفاهیم شی‌گرایی در سی‌شارپ — از ساخت کلاس‌ها تا طراحی سیستم‌های قابل توسعه، تمیز و حرفه‌ای

Classes

Class ستون فقرات برنامه‌نویسی شی‌گرا (OOP) است. کلاس در واقع یک قالب (Blueprint) برای ساخت اشیاء (Objects) است.

اگر بخواهیم ساده بگوییم:
Class = تعریف ساختار + رفتار

کلاس دقیقاً چیست؟

کلاس مشخص می‌کند:

  • یک شیء چه داده‌هایی دارد (Fields / Properties)
  • چه کارهایی می‌تواند انجام دهد (Methods)

خودِ کلاس شیء نیست؛ بلکه دستور ساخت شیء است.

مثال ساده از تعریف Class


class Person
{
    public string Name;
    public int Age;

    public void SayHello()
    {
        Console.WriteLine("Hello, my name is " + Name);
    }
}

اینجا:

  • Person یک Class است
  • Name و Age وضعیت شیء را نگه می‌دارند
  • SayHello رفتار شیء را مشخص می‌کند

ساخت Object از روی Class

برای استفاده از کلاس، باید از آن نمونه (Object / Instance) بسازیم: 


Person p = new Person();
p.Name = "Ali";
p.Age = 30;

p.SayHello();

حالا:

  • p یک Object واقعی در حافظه است
  • هر Object داده‌های مستقل خودش را دارد

چرا Class مهم است؟

  • کد را قابل فهم می‌کند
  • مدل دنیای واقعی را شبیه‌سازی می‌کند
  • نگهداری و توسعه را آسان می‌کند
  • پایهٔ Inheritance، Polymorphism و Encapsulation است

تفکر درست هنگام طراحی Class

یک Class خوب:

  • یک مسئولیت مشخص دارد
  • خیلی بزرگ و شلوغ نیست
  • نمایندهٔ یک مفهوم واقعی یا منطقی است
اگر نتوانی Class را در یک جمله توضیح بدهی، احتمالاً طراحی‌اش اشتباه است.

اشتباهات رایج تازه‌کارها

  • گذاشتن همه‌چیز داخل یک Class
  • استفادهٔ بیش‌ازحد از public
  • ساخت Class بدون هدف مشخص
  • قاتی‌کردن منطق‌های نامرتبط

تمرین‌های پیشنهادی

  1. یک Class به نام Car بساز با ویژگی‌های Model و Year
  2. یک متد بنویس که مشخصات ماشین را چاپ کند
  3. دو Object مختلف از Car بساز و مقادیر متفاوت بده

نکتهٔ حرفه‌ای

در پروژه‌های واقعی:

  • Fields معمولاً private هستند
  • دسترسی از طریق Properties انجام می‌شود
  • کلاس‌ها کوچک و هدفمند طراحی می‌شوند

Constructors

Constructor متدی ویژه است که دقیقاً در لحظهٔ ساخت یک Object اجرا می‌شود. وظیفهٔ آن: آماده‌سازی اولیهٔ شیء است.

هر وقت با new یک شیء می‌سازیم، یک Constructor اجرا می‌شود — چه آن را بنویسیم، چه ننویسیم.

Constructor چیست؟

Constructor:

  • نامش دقیقاً برابر نام Class است
  • نوع بازگشتی ندارد (حتی void)
  • برای مقداردهی اولیه استفاده می‌شود

مثال ساده


class Person
{
    public string Name;
    public int Age;

    public Person(string name, int age)
    {
        Name = name;
        Age = age;
    }
}

حالا برای ساخت Person: 


Person p = new Person("Ali", 30);

بدون Constructor، این Object ناقص ساخته می‌شد.

Default Constructor

اگر هیچ Constructor ننویسیم، C# به‌صورت خودکار یک Default Constructor بدون پارامتر می‌سازد: 


class Car
{
    public string Model;
}


Car c = new Car(); // مجاز

اما به محض نوشتن یک Constructor، Default Constructor دیگر ساخته نمی‌شود.

چند Constructor (Overloading)

یک Class می‌تواند چند Constructor داشته باشد: 


class User
{
    public string Username;
    public int Level;

    public User()
    {
        Username = "Guest";
        Level = 1;
    }

    public User(string username)
    {
        Username = username;
        Level = 1;
    }

    public User(string username, int level)
    {
        Username = username;
        Level = level;
    }
}

این کار باعث می‌شود Objectها انعطاف‌پذیر ساخته شوند.

Constructor Chaining

برای جلوگیری از تکرار کد، Constructorها می‌توانند همدیگر را صدا بزنند: 


class Product
{
    public string Name;
    public decimal Price;

    public Product(string name) : this(name, 0)
    {
    }

    public Product(string name, decimal price)
    {
        Name = name;
        Price = price;
    }
}

این الگو بسیار حرفه‌ای و تمیز است.

Constructor و اعتبارسنجی

یکی از مهم‌ترین کاربردهای Constructor: جلوگیری از ساخت Object نامعتبر است. 


class Account
{
    public decimal Balance;

    public Account(decimal balance)
    {
        if (balance < 0)
            throw new ArgumentException("Balance cannot be negative");

        Balance = balance;
    }
}

اشتباهات رایج

  • گذاشتن منطق سنگین داخل Constructor
  • ساخت Object ناقص
  • عدم اعتبارسنجی ورودی‌ها
  • تکرار کد بین Constructorها
Constructor باید Object را «سالم» تحویل بدهد، نه اینکه نصف کار را به آینده بسپارد.

تمرین‌های پیشنهادی

  1. یک Class به نام Book بساز با Title و Price
  2. یک Constructor بنویس که قیمت منفی را نپذیرد
  3. دو Constructor مختلف برای حالت ساده و کامل بنویس

نکتهٔ حرفه‌ای

در معماری‌های مدرن:

  • Constructor نقطهٔ اصلی Dependency Injection است
  • Object بعد از ساخت باید معتبر باشد
  • Immutable Objectها شدیداً به Constructor وابسته‌اند

مستندات رسمی: Constructors — Microsoft Docs

Primary Constructors

Primary Constructor قابلیتی جدید در C# مدرن است که اجازه می‌دهد سازنده را مستقیماً کنار تعریف کلاس بنویسیم.

هدف اصلی: کاهش Boilerplate Code و افزایش خوانایی.

مشکل Constructorهای سنتی

در C# کلاسیک، برای یک کلاس ساده، مجبور بودیم کد زیادی بنویسیم: 


class Person
{
    private string name;
    private int age;

    public Person(string name, int age)
    {
        this.name = name;
        this.age = age;
    }
}

این کد:

  • تکراری است
  • خوانایی کمتری دارد
  • برای کلاس‌های ساده آزاردهنده است

Primary Constructor چیست؟

با Primary Constructor، پارامترهای سازنده مستقیماً کنار نام کلاس نوشته می‌شوند: 


class Person(string name, int age)
{
}

همین! بدون نوشتن Constructor جداگانه.

دسترسی به پارامترها

پارامترهای Primary Constructor در کل بدنهٔ کلاس قابل استفاده هستند: 


class Person(string name, int age)
{
    public void Print()
    {
        Console.WriteLine($"{name} - {age}");
    }
}

ساخت Property از Primary Constructor

معمولاً Primary Constructor با Properties ترکیب می‌شود: 


class Person(string name, int age)
{
    public string Name { get; } = name;
    public int Age { get; } = age;
}

این الگو بسیار تمیز و حرفه‌ای است، مخصوصاً برای Objectهای Immutable.

مقایسه با Constructor معمولی

دو کد زیر از نظر عملکرد یکسان‌اند، اما دومی خواناتر است: 


// Traditional
class User
{
    public string Username { get; }

    public User(string username)
    {
        Username = username;
    }
}

// Primary Constructor
class User(string username)
{
    public string Username { get; } = username;
}

اعتبارسنجی در Primary Constructor

می‌توان در بدنهٔ کلاس اعتبارسنجی انجام داد: 


class Account(decimal balance)
{
    public decimal Balance { get; }

    public Account
    {
        if (balance < 0)
            throw new ArgumentException("Balance cannot be negative");

        Balance = balance;
    }
}

(این بلاک در زمان ساخت Object اجرا می‌شود)

Primary Constructor و Inheritance

در کلاس‌های مشتق، پارامترها به کلاس پایه پاس داده می‌شوند: 


class Animal(string name)
{
    public string Name { get; } = name;
}

class Dog(string name, int age) : Animal(name)
{
    public int Age { get; } = age;
}

چه زمانی استفاده کنیم؟

  • کلاس‌های ساده و Data-Oriented
  • Immutable Objectها
  • Record-like Design
  • DTOها و Modelها

چه زمانی استفاده نکنیم؟

  • کلاس‌های بسیار پیچیده
  • Constructor با منطق سنگین
  • وقتی خوانایی کاهش می‌یابد
Primary Constructor یعنی: تمرکز روی «چی هست» نه «چطور ساخته می‌شود».

تمرین‌های پیشنهادی

  1. یک Class به نام Order با Primary Constructor بساز
  2. Properties فقط خواندنی تعریف کن
  3. اعتبارسنجی مقدار منفی را اضافه کن

مستندات رسمی: Primary Constructors — Microsoft Docs

Fields

Field متغیری است که داخل یک Class تعریف می‌شود و برای نگهداری وضعیت داخلی (State) شیء استفاده می‌شود.

Fieldها نشان می‌دهند یک Object در چه وضعیتی قرار دارد، نه اینکه چه کاری انجام می‌دهد.

Field دقیقاً چیست؟

Field:

  • در سطح Class تعریف می‌شود
  • به ازای هر Object مقدار جداگانه دارد
  • در طول عمر Object زنده است

مثال ساده


class Person
{
    public string Name;
    public int Age;
}

در این مثال:

  • Name و Age Field هستند
  • هر Person مقدار مستقل خودش را دارد

Field و حافظه

Fieldها:

  • اگر Class باشد → روی Heap ذخیره می‌شوند
  • اگر Struct باشد → داخل خود Struct قرار می‌گیرند

این یعنی Field بخشی از ساختار واقعی Object در حافظه است.

چرا Fieldها مهم‌اند؟

  • نگهداری وضعیت داخلی
  • پایهٔ Properties
  • پایهٔ رفتارهای کلاس
  • کنترل منطق داخلی Object

مشکل Fieldهای Public

اگر Fieldها را public کنیم، کنترل Object از دست ما خارج می‌شود: 


class Account
{
    public decimal Balance;
}


Account acc = new Account();
acc.Balance = -1000; // ❌ وضعیت نامعتبر

این یعنی: Object می‌تواند همیشه در وضعیت غلط باشد.

الگوی درست: Private Field

Fieldها معمولاً private هستند: 


class Account
{
    private decimal balance;
}

و دسترسی از طریق Properties یا Methods انجام می‌شود.

نام‌گذاری Fieldها

در C# معمولاً:

  • Fieldهای private با _ شروع می‌شوند
  • camelCase یا _camelCase استفاده می‌شود

class User
{
    private string _username;
    private int _level;
}

Readonly Fields

اگر Field فقط یک‌بار مقداردهی شود، از readonly استفاده می‌کنیم: 


class Order
{
    private readonly int _id;

    public Order(int id)
    {
        _id = id;
    }
}

این کار به Immutable Design کمک می‌کند.

Static Fields

Fieldهای static متعلق به Class هستند، نه Object: 


class Counter
{
    public static int Total;
}

همهٔ Objectها این مقدار را به اشتراک می‌گذارند.

اشتباهات رایج

  • public کردن همهٔ Fieldها
  • استفاده از Field به‌جای Property
  • قرار دادن منطق داخل Field
  • نادیده گرفتن readonly
Field خوب یعنی: وضعیت داخلی امن و قابل کنترل.

تمرین‌های پیشنهادی

  1. یک Class به نام BankAccount بساز
  2. یک Field خصوصی برای موجودی تعریف کن
  3. از Constructor برای مقداردهی استفاده کن

نکتهٔ حرفه‌ای

در کد حرفه‌ای:

  • Field تقریباً همیشه private است
  • ارتباط مستقیم با بیرون ندارد
  • پایهٔ Encapsulation است

مستندات رسمی: Fields — Microsoft Docs

Methods

Method عملی است که یک Object می‌تواند انجام دهد. متدها منطق اجرایی و رفتار یک Class را تعریف می‌کنند.

اگر Fieldها وضعیت داخلی را نگه دارند، Methodها تعیین می‌کنند با آن وضعیت چه کاری انجام شود.

Method چیست؟

Method:

  • داخل Class تعریف می‌شود
  • می‌تواند ورودی (Parameter) بگیرد
  • می‌تواند خروجی (Return Value) داشته باشد
  • به وضعیت داخلی Object دسترسی دارد

مثال ساده


class Calculator
{
    public int Add(int a, int b)
    {
        return a + b;
    }
}

این متد:

  • دو عدد می‌گیرد
  • حاصل جمع را برمی‌گرداند
  • منطق مشخص و واضح دارد

متدهایی بدون خروجی

اگر متدی مقداری برنگرداند، از void استفاده می‌کنیم: 


class Logger
{
    public void Log(string message)
    {
        Console.WriteLine(message);
    }
}

دسترسی Method به Fieldها

Methodها می‌توانند Fieldهای private را مدیریت کنند: 


class BankAccount
{
    private decimal _balance;

    public void Deposit(decimal amount)
    {
        if (amount <= 0)
            return;

        _balance += amount;
    }
}

اینجا:

  • منطق اعتبارسنجی داخل Method است
  • Field مستقیم از بیرون دستکاری نمی‌شود

Method Overloading

یک Class می‌تواند چند Method با یک نام اما پارامترهای متفاوت داشته باشد: 


class Printer
{
    public void Print(string text)
    {
        Console.WriteLine(text);
    }

    public void Print(int number)
    {
        Console.WriteLine(number);
    }
}

Method و Responsibility

یک Method خوب:

  • یک کار مشخص انجام می‌دهد
  • کوتاه و قابل فهم است
  • نامش دقیقاً هدفش را نشان می‌دهد
اگر Method را نمی‌توانی در یک جمله توضیح بدهی، احتمالاً بیش‌ازحد بزرگ شده است.

Static Methods

متدهای static به Object وابسته نیستند: 


class MathTools
{
    public static int Square(int x)
    {
        return x * x;
    }
}

این متد:

  • بدون ساخت Object قابل استفاده است
  • به وضعیت داخلی وابسته نیست

اشتباهات رایج

  • نوشتن Methodهای خیلی بزرگ
  • قرار دادن منطق‌های نامرتبط در یک Method
  • استفادهٔ بیش‌ازحد از static
  • دسترسی مستقیم به Fieldها

تمرین‌های پیشنهادی

  1. یک Class به نام Counter بساز
  2. Methodهای Increment و Reset اضافه کن
  3. از Field خصوصی برای نگهداری مقدار استفاده کن

نکتهٔ حرفه‌ای

در طراحی حرفه‌ای:

  • Methodها منطق را پنهان می‌کنند
  • Object باید خودش مسئول رفتار خودش باشد
  • Method نقطهٔ اصلی Encapsulation است

مستندات رسمی: Methods — Microsoft Docs

Access Modifiers

Access Modifier مشخص می‌کند چه کسی اجازه دارد به اعضای یک Class (Field، Method، Property و …) دسترسی داشته باشد.

این مفهوم پایهٔ اصلی Encapsulation و طراحی امن در OOP است.

چرا Access Modifiers مهم‌اند؟

بدون کنترل دسترسی:

  • هرکسی می‌تواند وضعیت داخلی Object را خراب کند
  • کلاس‌ها شکننده می‌شوند
  • تغییرات کوچک، کل سیستم را می‌شکنند

انواع Access Modifier در C#

  • public — در دسترس همه
  • private — فقط داخل همان Class
  • protected — Class و فرزندانش
  • internal — داخل همان Assembly
  • protected internal
  • private protected

public

عضو public از هرجایی قابل دسترسی است: 


class User
{
    public string Username;
}

استفادهٔ بیش‌ازحد از public معمولاً نشانهٔ طراحی ضعیف است.

private (مهم‌ترین)

private یعنی فقط خود Class اجازهٔ دسترسی دارد: 


class Account
{
    private decimal _balance;
}

این کار وضعیت داخلی Object را محافظت می‌کند.

protected

protected برای کلاس‌های قابل ارث‌بری استفاده می‌شود: 


class Animal
{
    protected int Age;
}


class Dog : Animal
{
    public void Grow()
    {
        Age++;
    }
}

internal

internal یعنی فقط داخل یک Assembly: 


internal class InternalService
{
}

معمولاً برای لایه‌های داخلی پروژه استفاده می‌شود.

ترکیب‌ها (Advanced)

protected internal:

  • یا در همان Assembly
  • یا در کلاس مشتق‌شده

private protected:

  • فقط در کلاس مشتق‌شده
  • و فقط داخل همان Assembly

Access Modifier پیش‌فرض

اگر چیزی ننویسیم:

  • Members → private
  • Class → internal

الگوی حرفه‌ای رایج


class Product
{
    private decimal _price;

    public decimal Price
    {
        get { return _price; }
    }
}

بیرون فقط می‌خواند، داخل کنترل می‌کند.

اشتباهات رایج

  • public کردن همه‌چیز
  • استفادهٔ نادرست از protected
  • نادیده گرفتن internal
  • طراحی بدون فکر به آینده
هر چیزی که public است، قولی است که به آینده داده‌ای.

تمرین‌های پیشنهادی

  1. یک Class بساز که فقط از طریق Method قابل تغییر باشد
  2. یک Field private تعریف کن و از بیرون دسترسی نده
  3. تفاوت protected و private را تست کن

نکتهٔ حرفه‌ای

در پروژه‌های بزرگ:

  • همه‌چیز private شروع می‌شود
  • فقط در صورت نیاز public می‌شود
  • API عمومی با وسواس طراحی می‌شود

مستندات رسمی: Access Modifiers — Microsoft Docs

Properties

Property راه استاندارد و حرفه‌ای برای دسترسی به داده‌های داخلی یک Class است. Propertyها ترکیبی از Field + Method + Access Control هستند.

اگر Field «دادهٔ خام» باشد، Property «دادهٔ کنترل‌شده» است.

چرا Property لازم است؟

Fieldهای public خطرناک‌اند: 


class Account
{
    public decimal Balance;
}


Account acc = new Account();
acc.Balance = -500; // ❌ وضعیت نامعتبر

Property این مشکل را حل می‌کند.

ساختار Property

Property شامل دو بخش است:

  • get — برای خواندن مقدار
  • set — برای تغییر مقدار

class Account
{
    private decimal _balance;

    public decimal Balance
    {
        get { return _balance; }
        set
        {
            if (value < 0)
                throw new ArgumentException("Invalid balance");

            _balance = value;
        }
    }
}

Auto-Implemented Properties

در بیشتر مواقع، نیازی به Field دستی نداریم: 


class User
{
    public string Username { get; set; }
}

C# خودش Field مخفی می‌سازد.

Read-Only Properties

اگر مقدار نباید بعد از ساخت تغییر کند: 


class Order
{
    public int Id { get; }

    public Order(int id)
    {
        Id = id;
    }
}

این الگو برای Immutable Objects بسیار مهم است.

Private Setter

گاهی می‌خواهیم:
بیرون فقط بخواند، داخل تغییر دهد: 


class Product
{
    public decimal Price { get; private set; }

    public void ChangePrice(decimal newPrice)
    {
        if (newPrice > 0)
            Price = newPrice;
    }
}

Expression-Bodied Properties

Propertyهای محاسباتی: 


class Rectangle
{
    public int Width { get; set; }
    public int Height { get; set; }

    public int Area => Width * Height;
}

Property و Encapsulation

Propertyها:

  • وضعیت داخلی را محافظت می‌کنند
  • منطق اعتبارسنجی را پنهان می‌کنند
  • API تمیز ارائه می‌دهند
Field را قایم کن، Property را نمایش بده.

اشتباهات رایج

  • Property بدون منطق (وقتی Field کافی است)
  • قرار دادن منطق سنگین در get
  • public setter بدون دلیل
  • عدم استفاده از private set

تمرین‌های پیشنهادی

  1. یک Class به نام Student بساز
  2. Property برای Name و Grade تعریف کن
  3. اجازه نده Grade منفی باشد

نکتهٔ حرفه‌ای

در معماری تمیز:

  • Field همیشه private است
  • Property API عمومی Class است
  • Setterها با وسواس باز می‌شوند
